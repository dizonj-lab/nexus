# Test plan · NEXUS v0.3.7

Deploy (`git pull`, then `./deploy/canvas.sh`, or `./deploy/buddy.sh` / `--lab`),
reload once, check the top left reads **v0.3.7**. Automated, Docker only:
`./poc/tests/run-all.sh` → `ALL PASSED`.

Start from **＋ New design** (its event bus Q1 is Amazon MSK). Type the commands
in the console.

## T1 · Kafka topics, producers and consumer groups

| # | Step | Expected |
|---|---|---|
| 1.1 | `add topic orders to Q1 partitions 12 key orderId ordered` | Q1 → Inspector → **Channels** lists topic orders: 12 partitions, replication factor 3, min.insync.replicas 2, retention, cleanup, key meaning orderId, ordering required |
| 1.2 | `publish SVC1 to Q1/orders event "OrderPlaced v1"` | The connection SVC1 → Q1 is labelled `→ orders`. Advisor: **ordering required but no key**, and **writes its database and publishes without an outbox** |
| 1.3 | `subscribe SVC2 to Q1/orders group billing` | Q1 → SVC2 labelled `orders → · billing`. Advisor: **can receive the same message twice but does not deduplicate** |
| 1.4 | Select SVC1 → Q1 | Inspector shows **Publishes to Q1**: topic, key, event, delivery (acks=all, idempotent producer), outbox |
| 1.5 | Select Q1 → SVC2 | **Consumes from Q1**: topic, consumer group, concurrency, acknowledge, idempotent, retries, dead-letter queue, ordering |
| 1.6 | `publish SVC1 to Q1/orders key orderId outbox` | The key and outbox findings clear; the label shows `key orderId` |
| 1.7 | Advisor → fix **Make processing idempotent** | The finding clears |
| 1.8 | Q1 → Channels: replication factor 2 | Finding: replication below the MSK best practice, with a fix to 3 / 2 and the AWS source |
| 1.9 | Q1 → Consumes: concurrency 10 on SVC2 | Finding: more consumers than partitions; some sit idle |

## T2 · Notification topic (SNS) and fan-out

| # | Step | Expected |
|---|---|---|
| 2.1 | `add sns`, then `add topic orders to NT1` | A **Notifications / event bus** component (Amazon SNS) with topic orders |
| 2.2 | `publish SVC1 to NT1/orders`, `subscribe SVC2 to NT1/orders protocol https`, `add function named "Mailer"`, `subscribe FN1 to NT1/orders protocol lambda` | Both subscriptions get the same rate (fan-out), not half each. Advisor: no filter policy |
| 2.3 | Load 5,000 | Advisor: SNS pushing straight to the function; fix **Insert a queue** → NT1 → queue → FN1. Also the SNS publish quota (300 messages/s in most Regions; check Service Quotas) |
| 2.4 | NT1 → Channels → orders: **FIFO topic** | Findings: the FIFO topic cannot deliver to SVC2 over HTTPS or to the function over Lambda (FIFO topics deliver only to SQS) |
| 2.5 | A subscription filter with 6 attributes, for example `a=1, b=2, c=3, d=4, e=5, f=6` | Refused: at most 5 attributes per filter policy |
| 2.6 | Kind: **Event bus with rules** (EventBridge) | The channels become event types; subscriptions are rule targets |
